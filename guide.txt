1. OVERVIEW & OBJECTIVES
--------------------------------------------------------------------------------
This project implements a production-grade, highly resilient Transactional Outbox 
pattern using Spring Boot (Java 21), PostgreSQL, and Apache Kafka. 

Repository Coordinates:
- Upstream Base: https://github.com/KHolodilin/spring-transactional-outbox-kafka
- License: Apache-2.0
- GitHub Target: https://github.com/nithinmkannal/spring-boot-transactional-outbox-kafka

Primary Objectives:
1. Solve Dual-Write Inconsistency: Ensure zero message loss and exact business state
   consistency between relational databases and Apache Kafka without distributed 2PC.
2. Multi-Stack Architectural Comparison:
   - Servlet + Platform Threads + JDBC (`order-service`)
   - Reactive WebFlux + Project Reactor + R2DBC (`order-service-reactive`)
   - Virtual Threads (Java 21 Project Loom) + JDBC (`order-service-vt`)
   - Change Data Capture (PostgreSQL Logical Replication + Debezium) (`order-service-debezium`)
3. Resilience Under Adverse Conditions:
   - Broker outages during and after DB transaction commits.
   - Transient database disconnections, lock contention, and worker crashes.
   - Consumer duplicate detection and exactly-once processing semantics at application level.
4. Production Observability:
   - End-to-end distributed tracing via OpenTelemetry and W3C Trace Context.
   - Comprehensive Micrometer metrics, Prometheus scraping, and Grafana dashboards.
   - Structured JSON logging exported to OpenSearch via Vector.

2. ARCHITECTURAL COMPARISON: OUTBOX DISPATCH STRATEGIES
================================================================================
The Transactional Outbox pattern writes domain events to an `outbox_events` table 
within the same ACID transaction as the business entity changes.

Below is an engineering comparison of the primary dispatch strategies:

+----------------------+--------------------+--------------------+--------------------+--------------------+
| Dimension            | 1. Scheduled Poll  | 2. Hybrid In-Memory| 3. Postgres NOTIFY | 4. CDC (Debezium)  |
|                      | (SKIP LOCKED)      | (Direct + Polling) | (LISTEN / NOTIFY)  | (WAL Log Miner)    |
+----------------------+--------------------+--------------------+--------------------+--------------------+
| End-to-End Latency   | 50ms - 1000ms      | Sub-10ms (instant  | 5ms - 20ms         | 5ms - 50ms         |
|                      | (polling cadence)  | in-memory dispatch)|                    |                    |
+----------------------+--------------------+--------------------+--------------------+--------------------+
| DB Resource Overhead | High (continuous   | Minimal (poll only | Low for notify;    | Very low (reads    |
|                      | SELECT queries)    | during recovery)   | fallback required  | Postgres WAL)      |
+----------------------+--------------------+--------------------+--------------------+--------------------+
| System Complexity    | Low (standard SQL) | Medium (in-memory  | Medium (dedicated  | High (requires     |
|                      |                    | queue + worker)    | connection pool)   | Kafka Connect)     |
+----------------------+--------------------+--------------------+--------------------+--------------------+
| Scalability          | Moderate (DB lock  | High (non-blocking | Limited by single  | Very High          |
|                      | contention)        | async publishing)  | listener connection| (distributed)      |
+----------------------+--------------------+--------------------+--------------------+--------------------+
| Ordering Guarantees  | By ID/sequence     | By partition key   | By notification    | Strict commit order|
+----------------------+--------------------+--------------------+--------------------+--------------------+
| Delivery Guarantee   | At-least-once      | At-least-once      | At-least-once      | At-least-once      |
+----------------------+--------------------+--------------------+--------------------+--------------------+

Architecture in this Project:
- Primary Fast Path: Hybrid In-Memory Queue with Spring TransactionSynchronization 
  `afterCommit()` hook for sub-millisecond dispatch.
- Resilient Fallback: Background Sweeper using `SELECT ... FOR UPDATE SKIP LOCKED` 
  to claim and publish any orphaned/interrupted events.
- Alternative Implementations: Dedicated Reactive (R2DBC), Virtual Threads (Loom), 
  and Debezium CDC modules for benchmarking.

4. DATA MODEL & LIFECYCLE
================================================================================

4.1 Database Schema (PostgreSQL)
--------------------------------------------------------------------------------
```sql
CREATE TABLE orders (
    id UUID PRIMARY KEY,
    customer_id VARCHAR(64) NOT NULL,
    total_amount NUMERIC(12, 2) NOT NULL,
    status VARCHAR(32) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE TABLE outbox_events (
    id UUID PRIMARY KEY,
    aggregate_type VARCHAR(64) NOT NULL,
    aggregate_id VARCHAR(64) NOT NULL,
    event_type VARCHAR(64) NOT NULL,
    payload JSONB NOT NULL,
    status VARCHAR(32) NOT NULL DEFAULT 'NEW',
    partition_state VARCHAR(32) NOT NULL DEFAULT 'ACTIVE',
    retry_count INT NOT NULL DEFAULT 0,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    error_message TEXT
);

CREATE INDEX idx_outbox_status_created 
ON outbox_events (status, created_at) 
WHERE status IN ('NEW', 'FAILED');

CREATE TABLE processed_events (
    event_id UUID PRIMARY KEY,
    consumer_group VARCHAR(64) NOT NULL,
    processed_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

4.2 Ingestion & Publication Flow
--------------------------------------------------------------------------------
1. Client sends `POST /api/v1/orders` with `Idempotency-Key` header.
2. In-memory Rate Limiter (Bucket4j) verifies request quota.
3. Service executes `@Transactional` business logic:
   - Inserts order into `orders`.
   - Inserts event into `outbox_events` (`status = 'NEW'`, `partition_state = 'ACTIVE'`).
   - Registers transaction completion key in `idempotency_keys`.
4. On Transaction Commit (`afterCommit` hook):
   - Outbox event ID is enqueued into an asynchronous bounded in-memory queue.
5. Batch Publisher Worker (`KafkaBatchPublisher`):
   - Drains queue in micro-batches (e.g. 50 items or 10ms timeout).
   - Asynchronously produces messages to Kafka topic `orders.events` with message key = `aggregate_id`.
   - On Kafka ACK: Updates outbox row to `status = 'PROCESSED'`.
6. Background Recovery Worker (`RecoveryWorker`):
   - Periodically queries `SELECT id FROM outbox_events WHERE status IN ('NEW', 'FAILED') AND updated_at < NOW() - INTERVAL '30s' FOR UPDATE SKIP LOCKED`.
   - Re-enqueues unacknowledged events to protect against node crashes during `afterCommit()`.

5. DELIVERY GUARANTEES & FAILURE MODE MATRIX
================================================================================

+-------------------------------------+---------------------------------+--------------------------------------+
| Failure Scenario                    | System Reaction                 | Recovery & Guarantee                 |
+-------------------------------------+---------------------------------+--------------------------------------+
| 1. DB Commit OK -> App crashes      | Event is persisted in DB with   | Recovery worker picks up event       |
|    before enqueueing to in-memory   | status='NEW'.                   | using `SKIP LOCKED` after threshold  |
|    queue                            |                                 | -> Published (At-least-once).        |
+-------------------------------------+---------------------------------+--------------------------------------+
| 2. DB Commit OK -> Kafka Broker     | Async Kafka producer fails with | Retry policy backoff kicks in;       |
|    down / network partitioned       | TimeoutException. Event status  | background recovery retries once     |
|                                     | set to 'FAILED'.                | Kafka is reachable again.            |
+-------------------------------------+---------------------------------+--------------------------------------+
| 3. Kafka Send OK -> DB status       | Kafka has event, but DB still   | Recovery worker re-publishes event.  |
|    update to 'PROCESSED' fails      | has status='NEW'.               | Consumer detects duplicate in        |
|    or worker dies                   |                                 | `processed_events` and skips it.     |
+-------------------------------------+---------------------------------+--------------------------------------+
| 4. Poison pill / serialization      | Event fails repeatedly up to    | Event is marked 'DEAD_LETTER' and    |
|    failure                          | `max_retries` (e.g., 5).        | moved to DLQ table/alerted.          |
+-------------------------------------+---------------------------------+--------------------------------------+
| 5. Duplicate Kafka message receipt  | Consumer intercepts event ID    | Event ID inserted atomically in DB;  |
|    at Notification Stub             | before processing.              | Duplicate rejected (Exactly-once UX).|
+-------------------------------------+---------------------------------+--------------------------------------+

7. BUILD, TEST & RUN INSTRUCTIONS
================================================================================

7.1 Prerequisites
--------------------------------------------------------------------------------
- JDK 21 (OpenJDK 21 or later)
- Apache Maven 3.9+
- Docker Engine & Docker Compose

Set Java 21 environment:
```bash
export JAVA_HOME=/opt/homebrew/opt/openjdk
export PATH=$JAVA_HOME/bin:$PATH
java -version
```

7.2 Build All Modules
--------------------------------------------------------------------------------
```bash
mvn clean compile -DskipTests
```

7.3 Run Unit & Contract Tests
--------------------------------------------------------------------------------
```bash
mvn test
```

7.4 Run with Docker Compose
--------------------------------------------------------------------------------
To start the standard Servlet environment with observability stack:
```bash
docker compose -f docker/compose.servlet.yml --profile observability up -d
```

To start the WebFlux Reactive stack:
```bash
docker compose -f docker/compose.reactive.yml --profile observability up -d
```

To start the Virtual Threads stack:
```bash
docker compose -f docker/compose.vt.yml --profile observability up -d
```

7.5 Access Observability Dashboards
--------------------------------------------------------------------------------
- Prometheus: http://localhost:9090
- Grafana: http://localhost:3000 (admin / admin)
- Jaeger Tracing: http://localhost:16686
- OpenSearch Dashboards: http://localhost:5601
